# Scratch 게임 제작 교훈 (Lessons)

이 문서는 컬렉션을 만들며 쌓인 **장르 선택·아키텍처·성능·디버깅·폐기 판단** 교훈을 모은다.  
특히 2026-07 **수박 게임(Suika)** 실험은 Scratch 한계와 설계 부채를 동시에 보여 준 사례다.

> 관련: [game-candidates.md](./game-candidates.md) · [games-queue.md](./games-queue.md)

---

## 1. 한 줄 요약

| 주제 | 교훈 |
|------|------|
| 장르 | Scratch는 **소수 액터·이벤트·격자/턴**에 강하고, **밀집 물리·전 쌍 검사**에 약하다. |
| 재미 | “유명한 장르 포팅”만으로는 부족하다. **위기·선택·연쇄 쾌감** 축이 없으면 밋밋하다. |
| 구조 | **진실의 공급원 하나**(리스트/보드). 클론은 연출, 판정은 스테이지. |
| 조건식 | `if` 조건에 쓰는 값은 **본문에서 읽지 말고 조건 전에 set**. |
| 성능 | 느린 중력의 상당수는 G 값이 아니라 **틱 레이트(FPS) 붕괴**. |
| 검증 | Python 규칙 시뮬로 로직은 볼 수 있어도, **Scratch 동기화·체감은 별개**. |
| 제품 | 학습 목표가 찼고 품질 상한에 부딪히면 **폐기하는 것도 공학**. |

## 2. 사례: 수박 게임 (2026-07, 폐기)

### 2.1 무엇을 시도했나

1. **원 물리 Suika** — 클론 + 속도/중력 + 원 충돌 분리 + 같은 레벨 합체  
2. **스테이지 리스트 합체 스캐너** — 판정을 물리 if에서 분리  
3. **성능 패치** — `broadcast and wait 물리틱` 제거, 정지 과일 스킵, 합체 패스 축소  
4. **격자판 개편** — 6×8 칸 드롭·중력·인접 합체(뿌요/주키퍼식 연쇄) + PNG UI  
5. **결론: 취소** — 폴더·플랜 삭제, 후보/큐에 폐기 기록

### 2.2 Scratch가 약한 부분 (한계에 가깝다)

| 한계 | 증상 |
|------|------|
| 인터프리터·프레임 예산 | 과일 N↑ → 한 틱이 길어짐 → FPS↓ → 낙하·합체가 “느린 것처럼” 보임 |
| 클론 × 전수 검사 | 클론마다 O(n) 보면 **O(n²)/프레임** |
| `broadcast and wait` | 모든 클론 물리 직렬 대기는 정확하지만 **한 프레임에 몰빵** |
| 클론 forever 분리 | 빠르지만 **리스트/변수 레이스**로 합체·레벨 불일치 |
| 전역 임시 변수 | `임시`, `r합`, `검사i` 재사용 → 판정이 랜덤처럼 깨짐 |

Scratch는 원래 **가벼운 상호작용·소수의 스프라이트**용이다.  
“매 프레임 강체 물리 + 전 쌍 합체”는 네이티브/웹 엔진 영역이다.

### 2.3 Scratch 탓만은 아닌 부분 (설계·장르)

- Suika 원작 재미 = **커짐 + 쌓임 + 아슬아슬한 패킹**. 격자에 넣으면 부피 쾌감이 사라지고, 칸을 키우면 보드가 터진다.  
- 격자 머지 재미 = **연쇄 길이 + 콤보 + 판 정리**. 중간 타협(2개 합쳐 다음 단계, 칸 크기 고정)은 **어느 쪽 쾌감도 약해질 수 있다**.  
- 최적화할수록 “속도 ↔ 합체 신뢰도” 트레이드오프가 생겼다. 엔진 없이도 나오는 고전 문제다.  
- 반지름이 상자 대비 크면 로직이 맞아도 **후반 패킹 파산** (플랫폼 무관).

### 2.4 반복된 실패 패턴

1. 합체를 물리/`복제되었을 때` 안에 넣음 → “드롭할 때만 되는 것처럼” 보임  
2. 스테이지 스캐너로 분리 → 방향은 맞음  
3. 느림 해결 위해 검사·물리틱 축소 → 합체 누락·정지 과일 미합체  
4. 다시 검사 늘림 → 또 느려짐  
5. 격자로 전환 → 부하는 줄었지만 **재미 축이 불명확**  
6. 폐기

“될 듯 말 듯”은 대개 **한 프레임 안에 깨지면 안 되는 불변조건**이 깨진 상태다.

### 2.5 치명적이었던 구체 버그 (교훈용)

| 버그 | 증상 | 교훈 |
|------|------|------|
| 합체 `if` 조건에서 **아직 set 안 한 `레벨`** 사용 | 조건이 항상 0/옛값 → **합체 영구 불발** | 조건에 쓰는 값은 **본문 앞**에서 set |
| 거리 계산을 `if` **안**에서 수행 | 한 프레임 늦은 값으로 판정 | 측정 → 그다음 if |
| 합체 후 클론이 `과레벨`을 다시 씀 | 합체 결과가 덮임 | 레벨·활성의 **단일 작성자** |
| 정지 과일 충돌/자석 스킵 | 붙은 같은 레벨이 영원히 안 합침 | “성능 스킵”이 핵심 루프를 끊지 않는지 확인 |
| 연쇄 1패스만 / 낮은 ID 스킵 | 1차만 되고 2차 합체 안 됨 | 합체 후 **재스캔 또는 다패스** |
| 공유 `검사i` 등으로 보드 표시와 판정 경합 | 간헐적 오동작 | 표시용 인덱스와 판정용 인덱스 분리 |

### 2.6 왜 “커지게” 격자 수박은 안 되나

- 칸 고정 + 비주얼만 키움 → 성장 쾌감 약함  
- 고레벨이 칸을 더 먹음 → 보드 즉시 답답, 밸런스 붕괴  
- Suika 핵심(자유 패킹)과 격자 핵심(연쇄·계획)을 **반씩만** 가져오면 밋밋함  

**규칙은 1칸 유지 + 합체 팝 연출** 정도가 Scratch에서 현실적인 “커짐” 타협이다.  
그래도 장르 재미가 안 나오면 포팅을 접는 편이 낫다.

## 3. 장르 선택 가이드 (이 컬렉션용)

### 3.1 Scratch에 잘 맞는 것

- 클릭/타이밍, 퀴즈, 단순 슈팅  
- **격자·레인·턴제** (쿠키 대 개미, 오델로, 버블 슈터식 스냅)  
- 클론이 많아도 **서로 전수 물리 검사가 없는** 구조  
- 이벤트 방송 + 짧은 루프  
- 한글 변수 “손잡이”로 밸런스 튜닝하는 액션 (폭탄 스쿼드, 캐슬 디펜스 등)

### 3.2 피하거나 각오할 것

| 장르 | 이유 |
|------|------|
| 밀집 원/강체 물리 (Suika, 본격 물리 샌드박스) | O(n²), FPS, 지터 |
| 고정밀 리듬 + 오디오 동기 | 환경별 타이밍 편차 (Beat Tap 폐기 사례) |
| 클론 수백 + 매 프레임 AI 전수 스캔 | 프레임 예산 초과 |
| “유명 인디 1:1 복제” | 엔진 가정이 Scratch와 다름 |

### 3.3 재미 체크리스트 (빌드 전)

새 후보를 고를 때 최소 2개는 강하게 답할 수 있어야 한다.

1. **위기**: 무엇이 플레이어를 긴장하게 하나?  
2. **선택**: 매 순간 “이 수 vs 저 수”가 있나?  
3. **쾌감**: 연쇄, 성장, 명중, 클리어 중 무엇이 강한가?  
4. **상한 n**: 최악 클론/칸 수가 Scratch에서 버틸 만한가?  
5. **학습 포인트**: 클론·리스트·방송·변수 손잡이 중 무엇을 가르치나?

## 4. 아키텍처 규칙

### 4.1 단일 진실 공급원 (Source of Truth)

```
보드/리스트 (스테이지가 씀)
    ↓ 읽기
클론/스프라이트 (위치·코스튬·이펙트만)
```

- **하지 말 것**: 클론과 스테이지가 둘 다 레벨·활성·칸 값을 쓰기  
- **할 것**: 드롭/합체/중력은 리스트만 갱신 → `보드표시`로 시각 동기화  

### 4.2 책임 분리

| 역할 | 담당 |
|------|------|
| 규칙 판정 | Stage (또는 한 스프라이트의 한 스크립트) |
| 이동·연출 | 클론 |
| 이펙트·사운드 | 전용 스프라이트 / 방송 |
| 입력 | 커서·플레이어 본체 |

### 4.3 조건·측정 순서

```
1) 필요한 값 전부 변수에 기록
2) if / 비교
3) 부수 효과 (리스트 수정, 방송)
```

`if` 본문 안에서 막 읽어 조건을 채우면, Scratch는 **본문 실행 전 조건을 평가**하므로 버그가 난다.

### 4.4 방송 설계

- `broadcast and wait`: **정확성 필요 + 수신자가 적을 때**  
- `broadcast` + 각자 forever: **가벼움 필요 + 공유 상태 경합 주의**  
- 한 방송이 “판정 + 표시 + 입력 해제”를 한 호흡에 끝내면 디버깅이 쉽다.

### 4.5 변수 위생

- 물리/합체/UI가 **같은 `임시`를 돌려 쓰지 말 것**  
- 루프 인덱스(`검사i`)를 표시 루프와 판정 루프가 공유하지 말 것  
- 스테이지 전역 vs 스프라이트 로컬 이름을 한글로는 같아도 **ID는 분리**

## 5. 성능

1. **O(n²) 을 매 프레임 돌리지 말 것.** 이벤트 시점(드롭·착지·충돌 1회)에만 전수 검사가 낫다.  
2. “중력 값을 올렸는데 느리다” → 먼저 **프레임이 도는지** 볼 것.  
3. 정지 객체 스킵은 이득이 크지만, **핵심 상호작용(합체·자석)을 끄면 안 된다.**  
4. 클론 상한을 규칙으로 박기 (격자 칸 수, 최대 적 수).  
5. 연출(이펙트 클론)은 짧게 살고 바로 삭제.

대략 감각:

- 동시 “무거운” 액터 **십수 개 이하** + 이벤트성 판정 → 안전권  
- 수십 개 + 매 프레임 전 쌍 → 위험권

## 6. 디버깅·검증

| 방법 | 볼 수 있는 것 | 못 보는 것 |
|------|----------------|------------|
| Python 규칙 시뮬 | 합체/중력/승패 로직 | Scratch 스케줄·방송 타이밍 |
| sb3 JSON 구조 검사 | parent/next, multi-parent, opcode | 실행 시 레이스 |
| Scratch에서 플레이 | 체감 재미·버그 | 원인 자동 분리 |

**순서 추천:** 규칙 시뮬(선택) → 구조 검사 → 플레이 → “불변조건” 단위로 원인 좁히기.

플레이 중 “안 됨”을 보면:

1. 데이터가 맞는가? (리스트 값이 기대와 같은가)  
2. 조건이 기대한 프레임에 도는가?  
3. 누가 그 값을 덮는가?

## 7. 빌드·에셋

- `.sb3` = zip + `project.json` + MD5 파일명 자산  
- UI는 **PNG로 통일**하는 편이 한글·스타일 제어에 유리 (SVG 텍스트 tofu 이슈)  
- 격자 좌표는 배경 PNG와 `X0,Y0,CELL` 상수를 **한 번에 다시 맞출 것**  
- 한글 손잡이(튜닝 변수)는 학습 목표와 직결 — 대표작 패턴 유지  

---

## 8. 폐기 판단 (Stop Rule)

다음이면 **더 고치지 말고 문서에 남기고 접기**:

1. 같은 트레이드오프(빠름↔정확)를 **3번 이상** 왕복했다.  
2. 재미 축이 장르 타협 때문에 **구조적으로** 약하다.  
3. Scratch 한계(성능·동기)와 장르 요구가 **정면 충돌**한다.  
4. 학습 포인트(클론·리스트·방송)는 이미 다른 게임으로 충분하다.

수박 게임은 1~4에 해당해 **2026-07-28 폐기**했다.  
실패가 아니라 **경계선을 확인한 샘플**로 취급한다.
